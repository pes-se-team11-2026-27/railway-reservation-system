# Deviations from the submitted SRS, SAD and Test Plan

Team 11, Railway Reservation System. Kept up to date each sprint and explained in the final demo.
Each entry says what the document said, what was built, why, and what it affects.

## Sprint 1

| # | Document | What the document says | What was built | Why | Impact |
|---|---|---|---|---|---|
| D1 | SAD 4.3 API design | `InventoryService.holdBerths(trainId, date, classId, quotaId, count)` returns a hold; `confirmAllocation(holdId)` | `booking.createHold({ runId, classCode, quotaCode, passengers })` orchestrates; `inventory.lockFreeBerths`, `markHeld`, `releaseHoldBerths` own the rows. `confirmAllocation` moves to Sprint 2 with payment | Bookings attach to a dated train run, not a train plus date, and holds carry passenger details. Confirmation only makes sense once payment exists | Same behaviour as RRS-F-005 and F-006; interface names differ |
| D2 | SAD 3.4 components | AllocationEngine as one component | `src/modules/allocation` split into `allocate.js` (pure rule), `queue.js` (RAC and waitlist state, advisory lock) and `tatkal.js` (window) | A pure rule can be unit tested without a database | Easier testing; same responsibility |
| D3 | SRS RTM, STP Section 4 | RRS-F-008 (passenger limit) is Medium and outside the RTM | Implemented and tested in Sprint 1 (TC-BOOK-04) | Small, and it sits next to the Tatkal check | One extra tested requirement |
| D4 | SRS RRS-F-002 | OTP is sent to the mobile number | The code is generated, hashed and checked as specified, but shown on screen outside production because there is no SMS provider yet | SMS delivery belongs with the notification work in Sprint 2 (SAD ADR-03). Bulk SMS in India needs DLT registration | Verification logic complete; delivery pending |
| D5 | SRS RRS-SR-003 | Sign in with sessions, second factor for staff | `POST /api/auth/login` checks the password and lockout (SR-005) but issues no session yet; no sign in page | Nothing in Sprint 1 needs a signed in user; sessions arrive with payment and staff roles in Sprint 2 | Booking holds are anonymous in Sprint 1 |
| D6 | SRS 3.1 user interfaces | Booking flow of search, selection, passenger details, payment | Search is the home page; class chips on results go straight to booking; station and date pickers, Swap, recent routes, previous and next day links | Fewer steps, under RRS-NF-006 (usability and accessibility). These are usability additions, not new functional requirements | Accessibility verified with axe-core: zero WCAG 2.2 AA violations |
| D7 | SRS RRS-NF-006 | WCAG 2.1 level AA | Built and checked against WCAG 2.2 AA, the newer version | 2.2 includes everything in 2.1 plus target size and focus rules | Stricter than required |
| D8 | STP Section 5, Section 6 | Integration tests with Testcontainers | A PostgreSQL 15 service container in GitHub Actions, Docker Compose locally | Simpler to run on every push with no extra library | Same coverage; STP v1.1 updated |
| D9 | SAD 3.6, 5.3; STP 6, 8, 14 | Jira for tracking; SonarCloud for static analysis | GitHub Issues and Projects for backlog, sprints and defects; ESLint and Jest coverage (line and branch) in CI | Issues, pull requests and the board live in one place. Coverage reports come from Jest. SonarCloud can still be added | SAD v1.1 and STP v1.1 updated |
| D10 | SRS acceptance example for RRS-F-005 | 200 requests against 10 free berths | Demo data has 8 general quota berths per coach, so TC-BOOK-01 expects 8 confirmations | Seed data shape (8 general plus 2 Tatkal berths per coach) | Same property tested: every free berth confirmed exactly once |
| D11 | SRS 1.4 (Tatkal) | Tatkal as a separate quota | RAC and waitlist positions are shared per class and applied to Tatkal too | Simplification for Sprint 1 | Revisit if Tatkal needs its own waitlist |
| D12 | Process (Part-2) | Repository owner reviews and merges every PR | In Sprint 1 authors merged their own PRs after green CI. The owner added review comments afterwards. ## Sprint 2

| # | Document | What the document says | What was built | Why | Impact |
|---|---|---|---|---|---|
| D14 | SAD 4.3 API design | `PaymentAdapter.initiatePayment(holdId, amount, currency)` | The public `POST /api/payments` takes only `holdId`; the amount is worked out on the server from the journey and fare rules, and any amount sent is ignored. Currency is INR throughout. The internal `initiatePayment({ holdId, amountPaise })` matches the SAD | An amount from the browser could be tampered with (SAD 3.9, STRIDE tampering) | Safer than the SAD wording; same behaviour |
| D15 | SRS RRS-F-002, UC-03 | An unverified account cannot reach payment; booking needs a signed in passenger | Booking pages, paying, the return page and tickets require a signed in passenger with a verified mobile. A passenger sign in page verifies the mobile in place. The hold API still accepts requests without a session, but such a hold cannot be paid for | The Sprint 1 gate function is now enforced everywhere money is involved | Closes the Sprint 1 gap noted in D5 |
| D16 | SRS RRS-F-019 | Administrators maintain schedules, quotas and fare rules with effective dates | Fare rules and quota rules (Tatkal opening time, passenger limits) are maintained in the console with effective dates. Train timetables and coach layouts are not editable in the console; they come from the seed data | Timetable editing would change every existing run and booking; out of reach for the sprint | Fares and quotas fully covered; schedules are data, not code, and can be changed by migration |
| D17 | SRS 3.3 external interfaces | SMS and email providers, payment gateway | A development message provider records each message as delivered with a reference; a test gateway page simulates the hosted page, and test refunds complete at once. Real providers plug in behind the same adapters | No provider accounts for a student project; bulk SMS in India needs DLT registration | Every message and payment path is real and tested; only delivery is simulated |
| D18 | SRS RRS-F-015 | Refunds follow slab rules | Slabs chosen and kept in settings: 48 hours or more, flat charge only (Rs 60 Sleeper, Rs 180 AC 3 tier); 12 to 48 hours, 25 percent with the flat charge as the minimum; 4 to 12 hours, 50 percent; closed under 4 hours. Waitlisted passengers pay Rs 20 clerkage. The convenience fee is not refunded. A booking is cancelled as a whole | The SRS names slabs without values; these follow the Indian Railways pattern | Values change through settings without code |
| D19 | SRS RRS-F-017 | At chart time, remaining waitlisted tickets are refunded | Before refunding, unsold Tatkal berths join the pool and promotion repeats until no berth is free or nobody waits; remaining waitlisted passengers are refunded less the clerkage | Releasing unsold Tatkal at chart time is Indian Railways practice; repeating promotion guarantees no berth is left empty while anyone waits | More passengers confirmed than a single pass would give |
| D20 | SRS RRS-SR-003 | A second factor for staff | The second factor is a time based one time code (RFC 6238) from an authenticator app. Demo staff accounts (admin1, clerk1, tte1) and their secrets are in the seed data and published for the demo only; in test mode the code page shows the current code | Authenticator apps need no SMS provider and work offline | Production would issue secrets per person at onboarding |
| D21 | SRS RRS-SR-001 | TLS 1.2 or higher everywhere | Docker builds a self signed certificate; the demo runs on https://localhost:3443 and the browser warns once | A certificate from a certificate authority needs a real domain | Production mounts a proper certificate; the TLS rules are the same |
| D22 | SRS RRS-SR-004 | 30 PNR lookups a minute per client | The limit is kept in the memory of the server process | One server in this deployment | Several servers would share the count through the database or a cache |
| D23 | Process | Reviewed PRs merged in order | PR #59 first contained unresolved merge conflict markers; review caught them, changes were requested, and they were removed before merge. PR #62 was opened before its prerequisite (#63) merged, so its CI failed until the branch was updated after #63 | Shows the review and CI gates working | No defect reached main |

The handheld being a PWA is **not** a deviation: the SRS names an Android 12 device, and SAD 3.6 chose a PWA (service worker, IndexedDB, html5-qrcode) that runs on it.

Test totals at the end of Sprint 2: 94 unit and 179 integration tests, all run by CI on every push, plus a card data scan of the database and a backup.
